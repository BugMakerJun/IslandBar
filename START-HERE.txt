===========================

START HERE, IN THIS ORDER
-------------------------

    ARCHITECTURE.md  -- how the code is laid out, which way the dependencies point,
                        where a feature lives, and how to build, test and verify it.
                        Rules that the compiler enforces are stated here.

    ROADMAP.md       -- what is being worked on now, in what order, and what counts
                        as done. Also lists the open functional items.

    Then, only when a specific fact is needed (a measurement, a failure and its
    cause, a decision and who made it), go to:

    FEATURES.md      -- WHAT IS ACTUALLY DONE, every feature marked A/B/C/D with
                        its evidence. ..\README.md overstates progress.
    HANDOFF.md       -- the full record, in Chinese: every round of work, every
                        measured number, including the attempts that failed.
    TESTING.md       -- how to reproduce each kind of measurement.
    reviews/         -- the transcripts of the outside reviews (ChatGPT, Gemini)
                        that every change is researched against.

Full cross-session handoff document:

                                    ..\README.md overstates progress; FEATURES.md
                                    marks every feature A/B/C/D with its evidence.

    HANDOFF.md   (same folder as this file, written in Chinese)

QUICK COMMANDS
--------------

Build and run the smoke test:

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\IslandBar\scripts\build.ps1" -Config Debug -RunSmoke

Build, then run the runtime self-test (exit code 0 == all passed):

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\IslandBar\scripts\build.ps1" -Config Debug
    .\IslandBar\build\Debug\src\Debug\island_bar.exe --self-test

Show the bar (hides the shell taskbar; restores it on exit):

    .\IslandBar\build\Debug\src\Debug\island_bar.exe

Other flags:

    --keep-taskbar    leave the native taskbar alone
    --demo            cycle collapsed/hover/expanded with no input needed
    --probe-taskbar   report whether this process may hide the shell taskbar
    --no-console      behave as if there were no console (diagnostic)
    --help            print the same list, plus how to run it from each shell

PHOTOGRAPH AN ANIMATION, FRAME BY FRAME (no pointer needed):

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\IslandBar\scripts\capture-card.ps1" `
        -Exe ".\IslandBar\build\Debug\src\Debug\island_bar.exe"

Three environment settings drive it, and they are the only way to watch a
transition on this machine -- a script cannot move the pointer, so the bar has to
perform the transition on a timer:

    ISLANDBAR_PANEL_MS       open the system panel after N ms, close it at
                             ISLANDBAR_PANEL_CLOSE_MS (see the script's -CloseMs)
    ISLANDBAR_PANEL_CYCLE_MS after the first close, toggle the panel every N ms --
                             the later transitions are where the faults live, so a
                             single open proves very little (see -CycleMs)
    ISLANDBAR_SLOWMO         multiply every transition's DURATION -- never the
                             frame interval, which is the quantity being measured
    ISLANDBAR_TRACE_CARD=1   one log line per frame of a card transition: interval,
                             eased progress, card rectangle, content opacity, window
                             region
    ISLANDBAR_HOVER_ICON=n   treat icon n of the application row as hovered, so a button
                             that only ever opens under the pointer can be photographed
                             (-1 = the last icon). The script cannot move the pointer.
    ISLANDBAR_NO_MEDIA=1     do not start the media reader at all, which is what the bar
                             looks like when nothing is playing. On this machine a player
                             runs all day, so this is the only way to photograph the IDLE
                             island -- where the pill itself carries the date, the weekday,
                             the time and the weather (see HANDOFF 8.46).
    ISLANDBAR_NO_FULLSCREEN=1
                             ignore a full-screen application in front. While a game has the
                             screen the bar stands down by design (HANDOFF 8.54), so on a
                             machine that is always playing one there is no way to
                             photograph the bar itself -- its tray, its row, its status line.
                             This is what the tray's own screenshot was taken with.
    ISLANDBAR_TRAY_PAGE=1    open the tray page (the card behind the three-dot button at
                             the right-hand end of the bar) at startup. The card is behind
                             a click on a control, and a script cannot click the bar on this
                             machine, so this is the only way to photograph it.
    ISLANDBAR_START_MS       press the START button after N ms, and every
                             ISLANDBAR_START_CYCLE_MS after that. The Start button is the
                             one control that has to inject input into the shell, so it
                             cannot be tried by hand from a script -- it needs a click.
                             ISLANDBAR_START_ROUTE=1..5 picks how the menu is asked for:
                             1 SendInput Ctrl+Esc, 2 the same held 40 ms, 3 keybd_event
                             Ctrl+Esc, 4 keybd_event Win, 5 activate the Start menu's own
                             application. Measured 2026-10-11: NONE of the five works
                             from a sandboxed session -- see HANDOFF 7.84.

Two facts about running the bar at all, both learned the hard way:

  * It is a GUI-subsystem binary and CANNOT start inside the restricted sandbox:
    it dies with STATUS_DLL_INIT_FAILED (0xC0000142), which looks like a broken
    program rather than a restricted one. Run it from a normal shell.
  * Start-Process may then refuse with "cannot be run completely because the system
    cannot find all the information required", naming no file and no reason. Use the
    .NET Process API with an explicit WorkingDirectory instead.

WHERE THE WEATHER'S POSITION COMES FROM (2026-10-12, HANDOFF 8.47):

    %USERPROFILE%\IslandBar\weather.txt   one line pins a city (or "lat,lon")
    no line there                         Windows' own location service is asked
                                          (WiFi/satellite -- NOT an IP lookup, which
                                          answers "Tokyo" on this machine because its
                                          traffic leaves through a proxy)

Ask the machine directly, without the bar:

    .\IslandBar\build\Debug\tools\geoprobe\Debug\geo_probe.exe

Copy it OUT of the project tree first (anything whose image lives under
C:\PROJECT\Taskbar starts at LOW integrity here), and expect a one-time Windows
consent prompt. The line to read is `position source`: WiFi or Satellite means the
machine worked it out itself, IPAddress means it asked a service across the network.

AND THE SAME FOR THE HOVER PREVIEW (2026-10-12, HANDOFF 8.51):

    .\IslandBar\build\Debug\tools\thumbprobe\Debug\thumb_probe.exe

Two windows of its own, a DWM live thumbnail between them, every HRESULT
printed -- because the bar's own preview reported S_OK from every call and drew
NOTHING, twice over. GREEN inside the destination window means the machine draws
thumbnails; the source rectangle must be stated explicitly (an empty rcSource,
which the documentation calls "the whole window", is "no content" here), and the
destination must be a TOP-LEVEL window (a child is refused with E_INVALIDARG).

READ THE LOG, NOT THE CONSOLE:

    %TEMP%\island_bar.log      timestamped, written every run, flushed per line

The console is unreliable for this program. It is a GUI-subsystem binary, and
with no console attached the CRT's stdout has an invalid descriptor (-1);
writing to it trips a debug assertion in lowio\isatty.cpp (dialog box) instead
of printing nothing. All console output therefore goes through a guard in
Log.cpp -- never call std::printf / std::wprintf directly in this project.
`--no-console` reproduces the console-less path on purpose.

The exit code of --probe-taskbar is meaningful: 0 = can hide the taskbar,
1 = blocked by UIPI, 2 = the taskbar failed to restore.

NOTE ON SHELLS: `& "path"` is PowerShell syntax. In cmd.exe, `&` is a command
separator, so `& "path"` fails with "& was unexpected at this time" and the
program never runs. In cmd, quote the path directly or use `start /wait ""`.
