我认为以下风险必须写进 HANDOFF。

必须处理的六项风险

1. 外部载荷解析与内存安全

WM_COPYDATA 中的 COPYDATASTRUCT 和数据指针都不应被当作永久有效的内存。接收处理期间应立即验证指针、cbData、命令类型和字段边界，并复制需要的数据；不能把原始载荷指针保存到异步任务中供稍后使用。

2. 钩子回调不能阻塞

不在 Explorer 的钩子回调中执行文件 I/O、等待其他进程、复杂日志格式化或耗时同步操作。否则，托盘更新频繁时可能影响 Shell 响应。

3. 缓存必须处理更新和注销

同一个图标可能发生 ADD、MODIFY、DELETE 和 SETVERSION。应根据身份及生命周期更新缓存，而不是简单地每捕获一次消息就追加一格。窗口销毁、进程退出、图标注销都应能清理过期记录。

4. Explorer 重启和版本升级

PIN 仅解决模块不会被正常卸载的一类问题，不代表模块在 Explorer 重启后仍然存在，也不保证 Windows 更新后的载荷布局不变。必须支持 Explorer 重启后的重新初始化，并对未知格式安全降级。

5. 安全产品、系统稳定性和诊断

即使只观察不修改函数体，注入 Explorer 仍然可能被安全产品关注。需要保留可诊断的加载失败、解析失败和异常记录，避免将 PIN 误认为崩溃风险已经消失。

6. 禁用与恢复必须分开定义

功能开关可以停止新学习，但无法保证从已经 PIN 的 Explorer 进程中立即卸载模块。退出 IslandBar 后，模块应停止依赖已关闭的 UI 或缓存服务，并能安全地继续驻留，直到 Explorer 自身退出。

我特别强调两个实现细节

第一，WM_COPYDATA 的接收返回值和处理时机。 接收端应按照实际协议返回正确结果，避免在消息处理期间做耗时工作。对无法识别的载荷，应拒绝解析或安全忽略，不能按旧结构继续读取。

第二，不能把“当前观察窗口内没有崩溃”当成“稳定性已经证明”。 你提供的 PIN 修复后零事件数据值得保留，但仍需要覆盖高频注册、反复注销、Explorer 重启、快速进程退出、异常载荷和连续运行等回归场景。

A. ODR：不只看 include guard

Include guard 解决的是同一翻译单元重复包含的问题，并不能保证多个翻译单元之间满足 ODR（One Definition Rule）。

重点查：

普通函数的实现是否错误地写在头文件中，且没有 inline 或模板等合法条件。

头文件是否定义了具有外部链接的全局变量。

非模板的全局对象是否在多个 .cpp 中重复定义。

同名类、函数或变量是否因不同宏配置而出现不一致的定义。

static 全局变量是否被误认为共享状态，实际却在每个翻译单元各自生成一份。

C++20 下，inline 变量可以合法地在多个翻译单元中出现符合规则的相同定义；但这不代表所有带 inline 的实现都天然正确。类定义、宏配置和 ODR-use 仍然需要一致。

B. windows.h：10 个直接包含并不是问题本身

10 个 .cpp 直接包含 windows.h，这个数字不值得单独优化。真正要查的是宏和头文件依赖。

建议在统一的平台头中明确处理：

C++
#ifndef NOMINMAX
#define NOMINMAX
#endif

#ifndef WIN32_LEAN_AND_MEAN
#define WIN32_LEAN_AND_MEAN
#endif

#include <windows.h>

如果使用了 Winsock，还要注意 winsock2.h 和 windows.h 的包含顺序。

不过，不要为了“统一”而盲目将所有 Windows API 包装成一个巨大公共头。更好的原则是：

只在确实需要 Windows API 的翻译单元中包含相关头文件。

宏配置在项目构建配置或统一的平台入口中保持一致。

头文件不要依赖调用方提前包含某个 Windows 头。

尽可能用前置声明减少依赖，但不要为了减少一个 include 而让类型完整性问题更难理解。

C. 头文件自包含：比抽查更可靠的办法

你已经抽查了 CardLayout.h、IslandWindow.h、Motion.h。下一步建议自动生成一个小型检查目标，对每个头文件分别编译：

C++
#include "core/Geometry.h"

int main() {
    return 0;
}

实际执行时，每个头文件都要单独生成这样的翻译单元，并使用项目同一套 include 路径、宏定义和编译选项。

这能发现“单独包含会失败，但因为别的头先被包含所以一直没暴露”的问题。

如果项目有大量只供内部使用的头文件，不必马上把所有私有头都当成公共 API；可以先覆盖跨目录使用的头文件，再扩大范围。

D. DLL 与 EXE 的静态 CRT 边界

这是我认为最需要结合 IslandBar 当前架构确认的一项。

你提到 EXE 使用静态 CRT。如果 hook DLL 也静态链接 CRT，那么 DLL 和 EXE 通常各自拥有独立的 CRT 状态。

因此要检查跨模块接口是否存在以下情况：

EXE 分配内存、DLL 释放内存，或者反过来。

在两个模块之间传递 std::string、std::vector 等 STL 对象。

跨模块传递 FILE*、CRT 内部对象或异常对象。

一个模块构造 C++ 对象，另一个模块直接析构。

两个模块对共享结构体的布局、对齐或编译选项不一致。

如果边界只传递固定布局的 POD 数据、整数、句柄，以及由接收方负责释放的资源，风险通常更容易控制。

另外，WM_COPYDATA 的 lParam 指向的 COPYDATASTRUCT 和载荷，只保证在发送消息处理期间有效。接收端需要在处理期间完成校验和必要的复制，不能把载荷指针存进缓存，等消息返回后再读取。

这项检查不要求你改成动态 CRT；重点是明确跨模块的所有权和 ABI 约定。

但如果 island_tray_hook.dll 已经不再属于正式架构，就应把它从正式交付依赖检查中移除，而不是继续为一条准备废弃的路径增加复杂度。

E. 编译通过，还应该确认哪些配置？

所有正式构建目标是否都使用统一的 C++ 标准和 Windows SDK 配置。

构建系统是否能正确识别新增头文件和源文件，不依赖某台机器的旧增量构建产物。

正式安装包能否从干净目录安装并启动，而不是依赖开发目录中的 DLL、配置文件或缓存。

不需要为了形式上完整而强行支持项目本来不打算支持的架构；只需验证实际承诺的构建目标。

【一、这个程序是什么（事实，不是设想）】

Windows 11 上替代系统任务栏的"灵动岛"式横条（C++20 + Win32 + D3D11 + Direct2D + DirectComposition，单 exe、静态 CRT、无运行时依赖，实测私有内存 75–100MB）。

它现在做这些事：
  1) 顶栏自己的一条 pill，三种状态（collapsed / hover / expanded）用可中断、继承位移与速度的 spring 动画切换，卡片内部内容 180-200ms ease-out 淡入淡出；窗口是 WS_EX_NOREDIRECTIONBITMAP + Composition SwapChain。

  3) 托盘卡片：把系统托盘里的图标画成格子，点一下等于点真实托盘图标（左键=应用自己的左键行为，右键=应用自己的右键菜单），鼠标指针不能动。

  6) 通知：读系统 Toast 数据库，把消息与通话显示成通知纸条。
  7) 天气（Windows 定位或 weather.txt 指定城市）、时钟、日期。
  8) 开始按钮（要向 shell 注入 Ctrl+Esc / Win 键）。
  9) 隐藏原生任务栏（ABM_SETSTATE 那条路），自己占位。
  10) 全部纯逻辑（布局、命中测试、动画、状态策略）有一份 900+ 断言的 --self-test。

【二、已经踩过、必须写进设计的硬约束（都有实测）】

图中的 render 和 platform_win32 可以分别读取领域状态，但它们不应该互相调用具体实现。需要联动时，由 application 协调，或者由明确的接口和命令完成。

具体规则：

domain 不依赖任何 Windows 头文件、图形库、文件系统访问层或应用主窗口。

application 可以使用 domain 类型，但不直接调用 SetWindowPos、SendMessage、D3D11CreateDevice 等平台 API。

render 读取不可变的绘制快照，不负责扫描窗口、查询媒体或读取托盘文件。

platform 负责把真实系统事件转换为应用事件，也负责执行应用下发的平台命令。

tray_protocol 只定义协议，不允许依赖 TrayLearn.cpp、IslandWindow.cpp 或 main.cpp。

main.cpp 负责组装对象、配置依赖、启动与退出，不承载具体业务规则。

tests 可以依赖被测试目标，但正式库不能反向依赖测试目标。

诊断工具可以调用正式接口，但正式程序不能因为运行时环境变量而暗中进入实验性注入路径。

例如，domain/HitTest.cpp 不应该直接调用 GetCursorPos()。正确做法是接收已经转换成应用坐标的指针位置：

C++
struct PointerPosition {
    float x;
    float y;
};

HitResult HitTest(
    const LayoutSnapshot& layout,
    PointerPosition pointer);

它只返回命中结果。之后由应用层决定生成什么命令，平台层才执行对应的操作。

但纯逻辑不代表所有代码都必须是无状态函数。 弹簧动画可以有 position、velocity、target 等内部状态；只要它不直接调用系统 API，并且更新过程可确定、可测试，就仍然属于纯逻辑核心。

    PUBLIC src

add_library(island_application STATIC
    src/app/AppStore.cpp
    src/app/Reducer.cpp
    src/app/CommandDispatcher.cpp
)

target_link_libraries(island_application
    PUBLIC island_domain
)

实际项目还要统一警告选项、Unicode 设置和平台宏。上面的片段只展示依赖关系，不是完整的 Windows 构建配置。

我会再加一条硬规则：island_domain 的编译目标不链接任何 Win32、D3D 或 D2D 库。这样即使有人不小心写进平台调用，也更容易在构建阶段发现。

二、状态与数据流转：选择什么模型？
2.1 我的选择：集中状态所有权 + 事件驱动更新 + 小型命令队列

不选择完整 ECS，不引入重量级消息总线，也不保留所有功能都各自轮询的现状。

更具体地说：

一个 AppStore：持有当前 UI 需要的权威状态。

一个 Reducer：将输入事件转换成新的状态。

一个 CommandDispatcher：执行需要访问系统的命令。

一组 Source 适配器：从 Windows、媒体、天气和托盘读取数据。

一个渲染循环：每帧读取状态快照、推进动画、绘制。

一个定时调度器：仅用于确实没有事件通知的系统能力。

这是一个轻量级的事件驱动架构，不是要求你把整个程序改成纯函数式框架。

2.2 状态和事件应该怎么定义？

例如，应用状态可以按业务域分开：

C++
struct AppState {
    IslandState island;
    TrayState tray;
    MediaState media;
    WindowStripState windows;
    NotificationState notifications;
    WeatherState weather;
    SystemPanelState systemPanel;
};

每个子状态只存 UI 和交互真正需要的数据，不把所有 Windows API 句柄、COM 接口、D3D 资源都塞进去。

例如：

C++
struct TrayItemState {
    TrayItemId id;
    IconSnapshot icon;
    std::wstring tooltip;
    bool visible;
    bool enabled;
};

struct TrayState {
    std::vector<TrayItemState> items;
    uint64_t revision = 0;
};

这里的 TrayItemId 应当是应用内部稳定的身份标识。不能简单地把“第 3 格”当成身份，因为图标排序或增删后位置会变化。实际托盘协议还需考虑 HWND、UID、GUID、图标生命周期以及注册版本。

事件可以是：

C++
struct PointerMoved { float x, y; };
struct IslandExpanded {};
struct TraySnapshotReceived { TraySnapshot snapshot; };
struct MediaSessionChanged { MediaSnapshot snapshot; };
struct WindowListChanged { WindowSnapshot snapshot; };
struct NotificationReceived { Notification notification; };
struct Tick { double deltaSeconds; };

这不是要求使用复杂的模板化 std::variant 框架。C++20 下用 std::variant、一个普通的 switch，或者一组显式处理函数都可以。一个人维护的项目，应该优先选择调试器容易跟踪的实现。

2.3 数据是怎么流转的？

Windows / COM / IPC / 定时查询

输入、媒体、窗口、托盘、通知、天气

Platform Adapters

校验数据、转换单位、处理生命周期、生成应用事件

AppStore + Reducer

统一更新状态，增加 revision，生成必要的副作用命令

Renderer

每帧读取状态并绘制

CommandDispatcher

执行系统命令并返回结果事件

例如，用户右键托盘图标：

窗口输入层收到右键消息。

命中测试根据当前布局找出图标 ID。

应用层根据图标能力生成 InvokeTrayContextMenu 命令。

平台适配器尝试已验证的托盘菜单触发机制。

结果或失败原因返回应用层，更新状态或记录诊断信息。

注意：状态机只能决定想执行什么，不能保证 Windows 或目标应用一定执行成功。 右键菜单能否出现，仍然取决于实际可用的系统机制、目标应用行为和权限边界。

2.4 为什么不是 ECS？

ECS 适合大量独立实体、统一批处理和复杂动态组件组合。IslandBar 的主体是几个稳定的业务域：托盘、媒体、通知、天气、窗口列表和卡片布局。

为了这些对象引入 Entity、Component、System、查询规则与生命周期管理，会增加抽象成本，而不明显减少现有问题。

也不建议引入大型消息总线。你需要的是几十种清晰的应用事件，而不是跨团队、跨服务的发布订阅平台。

对于一个人维护、事件稀疏、渲染频繁的桌面程序，集中状态所有权加显式事件分发，成本最低。

2.5 60fps 与轮询如何协调？

你现在最值得改进的，不是简单把轮询间隔从 5 秒改成 1 秒，而是把“绘制频率”和“系统查询频率”彻底分开。

三、进程与二进制：怎样正式化托盘观察边界？
3.1 先承认一个事实：注入模块不是普通插件

你的现状是：

island_bar.exe：主 UI。

island_tray_hook.dll：加载进 Explorer，观察注册并写文件。

主程序每 5 秒读取一次文件。

安装器只打包 EXE。

这里的关键问题不在于“多了一个 DLL”，而是跨进程组件没有被纳入正式的部署、通信和生命周期协议。

此外，WH_CALLWNDPROC 的观察模块实际运行在 Explorer 进程内部。它与 Explorer 共享进程的地址空间和故障域。即使它只观察消息，也不能把它视为完全隔离的进程。

3.2 我会怎样设计二进制边界？

island_bar.exe

UI、应用状态、动画、渲染、命令处理

版本化 IPC 协议

island_tray_observer.exe（可选）

生命周期管理、快照接收、健康状态、错误恢复

仅在技术上确实需要时使用进程内观察模块

Explorer 进程内观察模块（有条件启用）

最小化代码、验证载荷、复制数据、立即返回

这里有一个必须澄清的设计事实：如果观察目标确实要求在 Explorer 进程内执行代码，单独的辅助 EXE 不能凭空替代进程内模块。 它可以负责管理、通信、状态检查和数据消费，但不能在没有可行的系统接口时，直接读取另一个进程内部发生的同步消息。

所以我会保留两种实现模式：

模式 A：无注入模式。 如果存在足够可靠的公开系统接口，优先使用它。

模式 B：最小进程内观察模块 + 独立通信端。 仅在模式 A 无法提供所需信息时使用。

你已经实测全局钩子会破坏 Chromium/WebView2 渲染进程，因此设计中明确禁止 dwThreadId=0 的全局钩子。只允许经过明确筛选的目标进程/线程策略，而且不应因为增加一个新应用就默认对所有进程安装钩子。

另外，PIN 只能防止模块被正常卸载，并不能消除 DLL 代码错误、死锁、内存损坏或 Explorer 崩溃风险。模块应尽可能短小，不执行阻塞式工作，不在钩子回调中访问文件系统，不进行复杂解析。

3.3 文件轮询还是 IPC？

当前“DLL 写文件，主程序每 5 秒读一次”的方案有一个优点：实现简单，主程序与 DLL 不需要共享内存。

但它的问题也很明确：

数据变化最多要等到下一次轮询才被主程序看到。

需要处理部分写入、文件锁、过期数据、旧版本文件。

文件既是数据传输通道，又是持久化状态，两个职责混在一起。

无法直接区分“没有托盘变化”和“观察模块已经停止工作”。

我会把协议与传输层分开：

C++
struct TrayProtocolHeader {
    uint32_t magic;
    uint16_t version;
    uint16_t messageType;
    uint32_t payloadSize;
    uint64_t sequence;
};

这只是协议头的示意。真实实现需要定义字段宽度、对齐、字节序、最大载荷、字符串编码、版本兼容规则，以及错误消息。

数据流应当是：

Explorer 内模块收到目标消息。

仅在有效期内读取原始载荷，验证长度与必要字段。

复制为自有数据，不保存原始消息中的临时指针。

通过独立的通信端发布快照或变化事件。

主程序校验协议版本、序列号和数据完整性。

应用状态层合并数据，并清理过期或失效的条目。

IPC 可以考虑命名管道或其他有明确权限边界的本机 IPC。选择前要评估部署用户身份、权限级别和连接生命周期。对于小型桌面程序，不必为此引入网络协议栈。

如果当前文件方式已经足够稳定，也可以先保留，但要至少增加原子写入、版本字段、数据新鲜度、写入失败记录和过期快照处理。不需要为了“架构更先进”立即把文件换成共享内存。

3.4 值不值得把注入与托盘观察拆成辅助进程？

值得把生命周期管理与通信职责独立出来，但不保证值得增加一个始终运行的辅助 EXE。

原因：

Explorer 内模块的生命周期和主 UI 生命周期不同。

主程序退出后，观察模块可能仍然存在。

Explorer 重启时，需要重新初始化。

模块加载失败或数据中断时，主程序需要知道，而不是把“没有新文件”误判成“没有变化”。

独立辅助进程可以负责连接状态、版本协商、错误恢复与诊断日志。

不过，如果它只是每 5 秒读取一次文件再转发，增加辅助进程没有明显价值。

我更倾向于让主程序通过 IPC 直接接收变化；只有在必须持续管理注入模块或独立恢复机制时，才增加常驻辅助 EXE。

3.5 安装器、版本和故障处理

如果最终交付包含 EXE、辅助 EXE 和进程内 DLL，那么安装器必须把它们作为一个版本化的产品单元处理。

最低要求：

所有组件带同一套产品版本和协议版本。

安装器校验所需文件是否齐全。

启动时检测协议不兼容，并给出可诊断错误，而不是静默失败。

更新时避免新 EXE 与旧 DLL 混用。

退出与卸载流程明确处理仍在运行的辅助进程和 Explorer 模块。

主程序在托盘观察模块不可用时仍能正常启动和显示其他卡片。

观察模块崩溃或连接中断时，主程序能区分“功能不可用”和“托盘列表为空”。

至于“单 EXE”承诺，我会改成更精确的产品定义：

主程序采用单 EXE、静态 CRT、无需额外运行时安装；只有明确列出的可选系统集成组件需要单独部署。

这样不会为了维护单文件承诺而把所有代码强行塞进同一个二进制。

四、测试：从 900 条自检走向可定位的测试体系

你的 903 条 Check(...) 并不是坏事。它说明已经有大量行为规则被编码成可重复检查的内容。

真正的问题是：如果所有检查都集中在一个 8,561 行文件里，它们的覆盖范围、独立性和失败定位就难以判断。

我不会为了引入某个测试框架而先改写所有自检。先建立分层，再把现有检查迁移过去。

4.2 L1：纯逻辑测试应覆盖什么？

建议首先把下面这些现有检查从 Diagnostics.cpp 中迁出：

CardLayout 的边界、间距、尺寸约束。

三种 Island 状态之间的转换。

Spring 动画在中断时继承位置和速度。

命中测试在不同 DPI、缩放和窗口坐标下的结果。

托盘数据的 ADD、MODIFY、DELETE、SETVERSION 状态变化。

失效 HWND、重复注册、GUID/UID 匹配等边界。

TrayPress 的输入意图与最终生成的动作命令。

特别是弹簧动画：你已经有“可中断并继承位移与速度”的行为要求。这种行为非常适合单测，不必通过录屏或人工观察判断。

例如，测试可以断言：

动画中途切换目标后，位置不会跳变。

速度会按定义继承或转换。

达到稳定状态后，动画最终停止更新。

非法的 deltaSeconds 不会导致数值发散。

这些检查不需要启动主窗口，也不需要真实显示器。

4.3 L2：给系统副作用加可替换的接口

以托盘动作为例，不应让纯逻辑直接调用 PostMessage、SendMessageTimeout 或其他系统 API。

可以定义一个小接口：

C++
struct ITrayActionExecutor {
    virtual ~ITrayActionExecutor() = default;

    virtual ActionResult Execute(
        const TrayAction& action) = 0;
};

正式环境使用 Win32 实现；测试环境使用 Fake，实现记录收到的动作并返回预设结果。

这样可以验证：

命中第 N 个托盘图标后，生成的动作确实指向对应的身份。

左键与右键不会被混淆。

找不到有效目标时，不会执行动作。

执行失败后状态如何更新。

超时或目标失效时，错误结果能够被正确记录。

但要注意：Fake 测试只证明应用层生成了正确动作，不证明目标应用一定响应。 真实应用的回调行为仍然必须通过 L3/L4 测试。

4.4 L3：托盘与其他真实系统接口的集成测试

建议把真实系统测试分成明确的测试套件：

tray_protocol_tests：解析合法和非法载荷、版本不匹配、长度超限。

tray_lifecycle_tests：ADD/MODIFY/DELETE、重复事件、失效项清理。

tray_ipc_tests：连接中断、重新连接、旧序列号、观察端退出。

win32_window_tests：窗口创建、激活、最小化、DWM 缩略图资源释放。

media_integration_tests：会话切换、无会话、封面缺失、COM 失败。

notification_integration_tests：权限不足、数据库不可用、数据为空。

真实系统测试应当使用清晰的前置条件。比如托盘测试开始前先确认目标窗口、权限级别和观察模块状态，而不是把“图标没有出现”统一算作按压失败。

4.5 L4：黄金图像与端到端测试
黄金图像测试：有价值，但不应成为第一优先级

对于你的渲染器，黄金图像测试能捕捉：

字体与布局意外变化。

卡片尺寸、间距和透明度变化。

DPI 缩放导致的绘制差异。

动画稳定终态的视觉回归。

但 D3D11/D2D/DComp、字体栅格化和系统缩放会导致图像存在环境差异。不能简单地对所有像素做绝对相等判断。

我会先为纯绘制布局输出一个确定性的测试快照，例如卡片矩形、文本布局、圆角参数，再逐步引入渲染截图比较。截图测试需要固定系统缩放、字体、分辨率和渲染环境，并允许有限的像素误差。

端到端测试：围绕用户真正关心的行为

建议至少保留以下场景：

安装后启动，确认主窗口与关键卡片正常。

Island 的 collapsed、hover、expanded 状态转换正常。

媒体会话切换后信息更新，缺少封面或歌词时不崩溃。

托盘左键能触发已验证应用的真实行为。

托盘右键能触发已验证应用自己的菜单。

Explorer 重启后观察机制恢复，主程序仍然正常。

权限较高的目标应用不能响应时，给出明确诊断，而不是误报成功。

退出程序后，原生任务栏状态按约定恢复。

安装器缺少任何必需组件时能够检测并报告。

这些测试不能都在一个 --self-test 进程中完成，因为部分测试涉及真实应用、Explorer 生命周期或系统权限。应该由独立的 smoke/集成测试驱动。

五、对照现有项目：逐项找不足

下面以你提供的现实数据为依据，不把“规模大”直接等同于“架构差”。

5.1 按严重程度排序

S0：正式组件边界与部署不一致

最高优先级

EXE、Explorer 内 DLL、安装器和数据文件之间的关系尚未正式化；安装器只带 EXE，但运行时链路包含 DLL。需要先确定 DLL 是否仍属于正式架构，再统一构建、安装、版本和故障处理。

5.3 你可能高估了哪些指标？

我会特别提醒下面四件事：

第一，零告警不是零风险。 /W4 /WX 很好，但编译器无法证明你没有保存已失效的窗口句柄、使用过期托盘缓存，或在 Explorer 回调中做了危险操作。

第二，include guard 不等于模块化。 所有头文件都可以安全重复包含，但它们仍然可能形成循环依赖、过度耦合或巨大的编译依赖图。

第三，900 条断言不等于 900 个独立测试场景。 有些检查可能共享相同输入、重复验证相同条件，或者仅测试内部实现细节。应按行为类别统计覆盖，而不是只追求数量。

第四，单 EXE 不等于单一故障域。 你的主程序是一个 EXE，但 Explorer 内 DLL 实际在另一个进程的地址空间执行。产品边界应当按实际执行位置、生命周期和权限定义，而不是按文件数量定义。

还有一个容易忽视的地方：低内存与低复杂度不是同一个目标。 75–100MB 私有内存是很有价值的实测基线，但为了省几 MB 而把所有工作塞回主线程、共用全局状态，可能反而提高故障率。应优先测量和减少不必要的资源、重复查询与缓存，而不是牺牲架构边界。

六、如果真的从头做，我会按什么顺序开发？

我不会先把所有卡片、动画、托盘和通知同时做出来。应该先建立能够承载这些功能的骨架，再按风险逐步加入系统集成。

阶段 1：纯逻辑核心

建立 island_domain，实现布局、命中测试、三态动画和状态转换。先不创建任何 Win32 窗口，让核心测试可以独立运行。

阶段 2：最小可运行窗口

建立主窗口、D3D11/D2D/DComp 渲染和消息循环。接入领域状态，但不查询托盘、媒体和通知。

阶段 3：应用状态与调度

引入 AppStore、事件分发和命令执行接口。将动画更新与系统数据刷新分离。

阶段 4：逐个接入系统能力

依次接入窗口列表、系统面板、媒体、托盘、通知和天气。每接入一项，就增加对应的单测、契约测试和实机测试。

阶段 5：解决高风险托盘链路

在决定使用公开接口、文件传输还是 IPC 之前，先确定可验证的观察机制。只有确认需要 Explorer 内模块时，才正式建立该模块的版本、生命周期和故障处理协议。

阶段 6：安装、恢复与发布

在干净目录安装并启动，验证所有必需组件、任务栏隐藏与恢复、Explorer 重启后的恢复行为，以及卸载流程。

七、对现有项目的最终裁定

我认为你现在不需要“重新做一个 IslandBar”，而是需要把现有项目向这套架构收敛。

优先顺序应当是：

先正式化托盘组件边界：确定 DLL 是正式依赖还是废弃实验组件，并使构建、安装器、通信和版本保持一致。

拆分渲染与状态更新的职责：让渲染读取状态快照，避免帧循环直接承担全部系统查询和业务协调。

把纯逻辑与系统副作用隔离：优先覆盖布局、动画、状态转换、托盘缓存与动作决策。

重组测试体系：保留现有 903 条自检，按领域拆分，并补充真实托盘响应的实机回归。

最后拆大文件：先拆 CLI 分发和诊断测试，再考虑更深层的重构。

最关键的一句话是：

从头设计的价值，不是把 47,876 行变成更漂亮的目录树，而是让每个功能的状态由谁负责、数据从哪里来、系统副作用在哪里发生、失败后如何恢复，都能被明确指出并独立验证。

你现在已经有不少可复用的功能实现和实机证据。保留这些资产，先把边界和测试补齐，比推倒重写更容易得到一个可靠、低内存、可持续开发的 Windows 11 灵动岛任务栏。
