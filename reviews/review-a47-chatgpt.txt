第 52 轮评审：IslandBar 要不要换 UI 框架？

我的结论先放在最前面：不换渲染框架，采用“保留自绘 + 统一设计系统 + 先优化实测瓶颈”的混合方案。

这里的“混合”不是把 WinUI、WebView2 或 ImGui 塞进现有程序，而是把底层绘制继续交给 DirectComposition + Direct2D，上层统一布局规则、控件规范、动画规范与视觉设计令牌。先把现有界面做得漂亮，再决定是否存在必须由框架解决的问题。

原因很直接：IslandBar 不是普通的设置窗口。它有动态改变的窗口区域、永不激活的交互方式、托盘兼容逻辑，以及一套已经通过实机测试的自绘体系。换框架不等于自动获得更高性能，也不等于自动获得更好的设计。

你目前最明确的性能嫌疑，反而是不需要电平表时仍然每 33 毫秒醒来一次的音量线程。在没有先解决这个问题之前，重写 15,000 多行渲染和布局代码，成本与收益不成比例。

这里有三个必须区分的指标：

CPU 利用率：线程是否频繁唤醒、是否忙等、是否做了无效工作。

绘制耗时：CPU 构建绘制命令、布局和提交图形工作的成本。

呈现耗时：合成器何时真正显示帧，以及是否丢帧。

你测到的 slow frame 95~110 ms 如果后面明确记录了 no draw: the loop was waiting，就不能直接认定为渲染卡顿。反过来，hitches(>50 ms)=0 也不能单独证明所有输入与动画都流畅。

我建议先做的性能改动

P0：让 30 Hz 音量线程按需运行

电平表实际显示、需要实时刷新时才启动采样；面板关闭或电平表不可见时停止采样。注意保留音量变化通知等其他确实需要的更新路径。

验收：关闭电平表后，采样次数应停止增长；记录 60 秒 CPU、唤醒次数及句柄变化。

P1：区分等待、绘制与提交

分别记录帧循环等待时间、CPU 绘制耗时、GPU/合成器呈现间隔。不要仅依赖一个 slow frame 数值。

验收：静息态、展开动画、音乐播放三种场景分别输出可比较的统计数据。

P2：检查动态 Region 更新成本

测量每帧 SetWindowRgn 的调用次数、耗时与实际形状变化。若形状未变化，不应仅为了维持动画而重复设置同一个区域。

验收：记录静息态与 220→720 DIP 展开时的 Region 更新次数、CPU 耗时和动画帧间隔。

特别提醒： 当前 4 帧/秒的空闲节奏与 60 FPS 的动画节奏并不矛盾。但如果每次合成器时钟唤醒都会完整遍历状态、重建大量文本布局或更新窗口 Region，就仍然可能浪费 CPU。应该先量清楚，而不是把它归咎于自绘。

Q2：观感——框架能不能让它更好看？

能降低实现漂亮界面的难度，但不会自动把丑的布局变漂亮。

框架能提供的价值主要有四类：

1. 统一控件语言

Fluent 风格的按钮、开关、滑块、列表、焦点状态和禁用状态更容易保持一致。适合设置面板、声音输出列表等常规界面。

2. 更成熟的布局与状态管理

标准布局、滚动列表、键盘焦点、UI Automation（UIA）辅助功能树，可以减少自己维护控件状态的工作。但引入框架并不代表所有自绘内容自动获得无障碍支持。

3. 设计工具与主题资源

设计令牌、控件模板、主题资源和设计预览能提高迭代效率。Mica、Acrylic 等材质则取决于具体框架、窗口配置和系统支持，不是换框架就一定能获得。

但你这版真正的观感问题是什么？

结合第 49 轮提供的实测结构，我认为主要是设计规则尚未统一：

磁贴标签在盒子外面，图标与文字没有统一对齐线。

磁贴是厚重的圆角盒子，音量与亮度却是极细的线条。

托盘页留白太多，图标容器又偏小。

卡片标题、控件标签和辅助文字的层级不够明确。

应用图标行与托盘网格的容器语言不一致。

这些问题即使全部改用 WinUI，也仍然可能存在。

我的建议是先定一套设计系统，再用现有 Direct2D 实现。 例如，先统一 4/8/12/16 DIP 间距体系、8/12/16 DIP 圆角等级、标题/正文/辅助文字三级字号，以及卡片与磁贴的明暗层级。具体视觉参数应以实际截图校准，而不是把这些数值直接当成最终答案。

这样能先回答一个关键问题：如果不换框架，现有程序能否达到你要的高级、协调、精致的效果？ 我认为完全值得先验证。

Q5：最终方案——混合，但不混入新的 UI 运行时

我建议把工作分成三个阶段。

第一阶段：保留渲染架构，统一设计系统。

不改 DirectComposition、Direct2D、窗口 Region 和 FrameState 流程。先统一磁贴、滑条、托盘图标、卡片标题、边距、圆角、描边和悬停反馈。

第二阶段：优化真实性能热点。

优先处理无效的 30 Hz 音量采样，再评估 Region 更新、文本布局缓存、重复绘制与无效唤醒。每项优化都要有前后实测。

第三阶段：按需补足原生控件能力。

仅在确认有必要时，为键盘导航、无障碍或复杂列表实现原生接口；如果某个表面确实无法合理实现，再单独评估框架原型。原型不得直接替换主界面。

UI 技术选型约束

IslandBar 默认采用原生 Win32 + DirectComposition + Direct2D/DirectWrite 自绘架构，不因视觉美化或未经验证的性能预期整体迁移 UI 框架。

界面一致性优先通过统一的设计令牌、布局规则、控件规范和状态反馈实现。性能优化必须以可复现的实测瓶颈为依据。

引入任何新的 UI 框架或运行时之前，必须提供独立原型，并验证动态窗口区域、NOACTIVATE、命中测试、动画、CPU/GPU 占用、内存、启动时间、部署依赖及 /W4 /WX 构建要求。

任何候选方案均不得破坏现有纯逻辑断言、层方向约束和固定场景回归。原有测试应按语义迁移，不得仅因实现变化而删除。未经评审与用户确认，不得替换主渲染路径。

最终表态：不换整体框架；采用设计系统层面的混合方案。 先让现有自绘界面达到理想观感，再用性能数据决定是否值得引入任何额外技术。这样既不浪费已经验证过的底层能力，也不会因为追求“框架自带的漂亮控件”而引入新的运行时、部署和窗口兼容性问题。
