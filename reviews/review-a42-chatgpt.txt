Q2：重复代码到底什么时候抽？

我建议 ARCHITECTURE 直接写成这个判据：

重复代码判据

只有当两段代码同时满足“语义相同 + 变化原因相同 + 修改应保持同步”时才抽取。

仅仅因为代码文本相似、行数相似或能够写成同一个函数，不得抽取。

如果两段代码未来可能因职责不同而独立变化，即使当前实现完全相同，也允许保留重复。

这个判据非常重要。

套到你现在 B
① CLI demo 搭建

这个我：

强烈同意抽。

帧循环

本质上是同一个“构建测试/演示环境”。

而且一次抽掉 5 组。

这是非常好的重复。

② Renderer 纹理描述

同意抽。

如果两处确实是同一个纹理描述协议，那么属于：

同一概念、同一变化原因。

③ Lyrics 报告填充

反对现在抽。

即使看起来只有几行。

如果：

纯文本

歌词报告

以后字段变化方向不同，那么抽出来只是在增加一个：

纯文本

反而让调用关系更绕。

④ TrayLearn / TrayPress

倾向保留。

除非能证明它们共享的是一个真正的领域概念。

如果只是：

C++
某几个字段赋值
某几个状态填充

不要为了消灭 5 行重复代码去制造抽象。

⑤ TrayPress 内部重复

如果两处实际上就是：

纯文本
同一个状态转换
同一个不变量
同一个未来修改点

可以抽。

否则保留。

“文件该不该继续拆”的 ARCHITECTURE 判据

我建议写成：

文件拆分判据

只有当一个文件同时承载两个以上独立变化原因，且可以形成稳定的职责边界时才拆分。

单纯因为文件超过某个行数、函数数量多、或者视觉上“不好看”，不足以触发拆分。

拆分后每个新文件必须能够用一句话描述其唯一职责；否则不拆。

这个判据比：

“超过 3000 行必须拆”

高级很多。

纯文本

却可能包含：

媒体
绘制
报告

所以前者可以不拆，后者应该拆。

Q3：volumeChanged 怎么办？

我的明确答案：

接进去。

但不要直接改完就算结束。

先定义它的语义：

纯文本
volumeChanged == true
        ↓
本帧需要重新生成受音量影响的视觉内容
        ↓
needDraw == true

如果当前 UI 确实有音量相关显示，那么：

C++
needDraw =
    ...
    || volumeChanged;

是符合原来注释意图的。

为什么不是删除？

因为删除意味着：

“音量变化不需要重绘。”

这其实是在改变产品行为，而不是清理死代码。

现在真正的问题是：

纯文本
代码意图 ≠ 实际执行路径

所以应该：

先接入 → 加针对性 self-test → smoke → 固定日志确认。

如果测试证明音量变化确实应该驱动重绘，那债就还完了。

如果测试证明音量变化实际上不应该影响当前画面，再把 volumeChanged 连同注释一起删掉。

不要“保留原样并记录”。

因为那会让一个已经知道有问题的逻辑继续存在。
