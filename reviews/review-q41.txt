─ 1. 债的现状（全部是实测，不是印象）

**A. 分层只锁住了一层。** `island_domain` 是独立静态库，`domain/` 里不许出现 `<windows.h>`
（`domain/PurityCheck.cpp` 编译期护栏 + 该目标不链接任何库）。其余 `app/ render/ media/ shell/
platform/ services/ cli/` **都在同一个 exe 目标里**：ARCHITECTURE.md 第 3 节甚至写明"这些之间可以互相
调用，但共用的类型都来自 core/"——所以现在**没有任何东西**阻止一条反向 include 进来。

我扫了一遍真实的跨层 include（源文件与头文件都扫了），依赖图是这样（箭头＝"包含"）：

```
app    -> platform, render, media, services, shell
render -> media, services, shell, platform      (TextRenderer 要 shell/TrayIcons.h、shell/StartApps.h)
shell  -> media, platform, domain
services -> media, domain
media  -> domain
platform -> domain
core   -> (无)
domain -> (无)
```

**唯一的回边**：`platform/GlassMaterial.h` 包含 `render/Theme.h`（它是那条"阴影 + 颗粒 + 高光"的画法，
用的是 Theme 里的材质常量），而 render 侧（`Renderer.cpp` / `TextRenderer.cpp`）又包含
`platform/GlassMaterial.h`。除此之外 platform/media/services/shell/core/domain **没有一处**包含 render/。
所以"按依赖方向切静态库目标"这条路，只差把 GlassMaterial 挪到 render/ 这一件事（`render/Theme.h` 自己只
包含 windows.h / d2d1_3.h / string，不会把回边带回来）。

**B. `RunBar` 是一个 5857 行文件里的一个 5200 行函数。** `main.cpp` 5857 行，`int RunBar(...)` 从第 635 行
一直到文件末尾，**没有第二个函数**。状态已经搬出去过了（`app/BarState.h` 25+26+20 个字段、`app/BarSystems.h`
22 个对象——ROADMAP 第 1 节的 10 片全 ✅），所以现在剩下的是**一个函数里的相位**，注释已经把它们分好了：
材质 / AppBar / strip 归还 / 本地推送通道 / 正在播什么 / 不发布会话的播放器 / 歌词 / 输出音量 /
声音输出页 / 天气 / 悬停预览 / 系统托盘 / 托盘学习 / 开始卡片 / 任务条窗口列表 / 显示策略 / 内存行 /
节流行 / 诊断注入 / 通知 / 全屏判定 / 按下与拖动 / 悬停与状态 / 动画推进 / 绘制 …
主循环从 1578 行开始（`while (true)`），前面 900 多行是**一次性构造**（每个模块的 Open/Start/Create）。

**C. 没有任何自动化回归。** `--self-test` 只能测纯逻辑（1001 条），栏的真实行为靠人看。托盘那条链路尤其

**Q3 RunBar 怎么拆**（这是我最不确定的一处）。候选：

─ 4. 约束（照仓库规范，请在这个框子里给建议）

* 分层目标：`domain / core / app / render / media / shell / platform / services / cli`；domain 不许出现 Win32。
