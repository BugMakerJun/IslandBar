针对第 51 轮评审（关于 SystemSettings.exe 幽灵弹窗与灵动岛机制关联排查），以下是我们的逐条表态、机制排序与可执行方案：

Q1. 机制排序与遗漏机制

机制排序（从最高嫌疑到最低）：

M-A / M-D（通知区被完全隐藏 / 任务栏生态位缺失）：最高嫌疑。Global.Accounts 和 DesktopSpotlight 等微软系后台任务在尝试同步凭据或推送通知时，如果发现底层的 TrayNotifyWnd 被完全隐藏或失效，Windows 系统的容错机制会直接降级唤醒 SystemSettings.exe 来索取用户交互。

M-F（遗漏的遗漏：未正式注册为系统 AppBar）：【新补充机制】。如果 IslandBar 只是简单覆盖在最顶层（TopMost）而没有向 Windows 注册标准的 SHAppBarMessage (ABM_NEW)，在 Windows 看来，桌面上“没有合法的任务栏和通知区”，系统底层组件会周期性地启动自检或修复引导（即无缘无故弹出设置页）。

M-B / M-C（Explorer 钩子与广播）：中等嫌疑。

M-E（纯巧合背景任务）：最低嫌疑（虽然 21:07–22:32 没弹，但由于用户不在机旁，不能排除）。

Q2. 第一步（诊断开关）值得加吗？

表态：不仅值得加，而且是执行第二步对照测试的前提。

理由：如果没有环境变量或命令行开关（如 --no-hook、--no-broadcast、--keep-tray），第二步的对照测试根本无法在不重新编译打包的前提下灵活切换。因此，第一步必须做。

Q3. 三段对照的顺序与时长

推荐顺序与时长（每段至少 90–120 分钟活跃使用）：

对照组 A（验证 M-A/M-D/M-F）：开启栏，但不完全隐藏任务栏（采用老版“裁剪到只剩通知区”或保持托盘可见）。如果 2 小时内不再弹出，直接锁定元凶是“完全隐藏任务栏/通知区”。

对照组 B（验证 M-B/M-C）：恢复隐藏任务栏，但关闭 Explorer 注入钩子与广播。如果不再弹出，锁定钩子冲突。

对照组 C（终极净空测试）：彻底关闭 IslandBar，用户正常办公 2 小时。若依然弹出，则实锤是 Global.Accounts 自身的系统 Bug（与我们无关）。

Q4. 第三步的两条修法，哪条更干净？

表态：毫无疑问，选“裁剪任务栏 / 让通知区对 Windows 保持存在”这路线（回归 2026-10-15 的裁剪逻辑）。

理由：完全隐藏 Shell_TrayWnd 和 TrayNotifyWnd 是在和 Windows 底层 Explorer 的状态机“硬刚”。把任务栏裁剪到只剩通知区（或将其移出可视区但保留句柄与消息循环），在 Windows 眼里“通知区依然活着”，既能达到我们视觉清爽的目的，又能彻底切断系统组件因找不到通知区而疯狂派生 SystemSettings.exe 的诱因。

Q5. 兜底：如果机制不确定，要不要“自动关掉别人的窗口”？

表态：绝对反对自动干预/强杀其他窗口。

理由：强行 TerminateProcess 或隐藏属于外部进程的 SystemSettings.exe 是极其危险的黑客式做法，极易引发 Windows 错误日志、挂起甚至被杀毒软件误杀。

正确做法：如果短时间内无法根绝，最多在后台加一个“幽灵设置窗拦截日志”（只打日志，绝不干预），把精力集中在修复 AppBar 注册 和 通知区裁剪保留 上。

Q6. 这一轮的验收标准该怎么写？

验收条件：

环境日志：IslandBar 启动日志中明确输出当前机制测试参数（如 [Config] TrayMode=Cropped, ExplorerHook=Disabled）。

黄金指标：在用户连续进行日常办公（含联网、应用切换、通知触发）的 4 小时内，系统任务管理器与事件查看器中 SystemSettings.exe 的异常自启次数为 0。

视觉指标：在保证系统不再乱弹窗的前提下，顶部栏依然完美呈现设计意图，无遮挡、无性能劣化。
