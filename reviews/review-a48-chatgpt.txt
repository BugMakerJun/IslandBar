第 53 轮评审：IslandBar 液态玻璃开发方案

我的结论：修正规矩，采用 C → A → B 的分阶段路线。第一阶段先把现有自绘材质做得足够高级；第二阶段用一个最小独立窗口探针验证 DWM Acrylic 能否满足胶囊的形状与裁剪要求；第三阶段只有在前两条无法满足目标、且实测预算允许时，才进入 GPU 抓屏与折射实验。

我不同意现在就上 B，也不同意因为旧规矩禁止背景模糊，就直接放弃真实玻璃。

关键是把三件事分开：

玻璃的观感：高光、边缘、透亮、染色、动态形变。现有 Direct2D 就能做出很大一部分。

真实的背景模糊：需要背景像素，但并不等于必须抓屏；应该先验证 DWM 能否在严格限定的胶囊窗口中完成。

真实折射：必须让背景采样位置发生空间位移。纯渐变、描边和高光无法真正实现这一点；但它也不意味着必须立刻引入抓屏系统。

这次目标是让岛看起来像一块有厚度、有反射、会流动的玻璃，而不是把当前黑色胶囊简单调成半透明灰色。

一、先明确三条路线的取舍
C：自绘液态材质
第一阶段

保留现有 DirectComposition + Direct2D 渲染链。强化双层边缘、镜面高光、动态反射、透亮层次、主题染色和胶囊形变。

优点： 不抓屏、不增加运行时依赖、成本可控、兼容现有卡片动画。

缺点： 没有真实背景折射，也无法准确模糊动态壁纸内容。

A：独立 DWM Acrylic 胶囊窗口
第二阶段探针

让系统负责背景采样和模糊，IslandBar 继续负责内容与动画。前提是必须验证圆角外溢、层级和动态窗口调整。

优点： 有机会以较低的实现复杂度获得真实背景模糊。

缺点： 圆角外观不等于 Acrylic 背景一定按相同轮廓裁剪；系统背板、窗口透明方式和合成路径也可能影响结果。

B：GPU 抓屏与折射效果链
第三阶段研究

获取背景纹理，在 GPU 上进行模糊、位移采样、色调处理和合成。

优点： 三条路线中，自主控制背景折射最充分，能按胶囊轮廓设计透镜效果。

缺点： 捕获排除、反馈环、显示器多样性、遮挡关系、显存同步和 GPU 成本都要单独解决。

这里的排序是开发顺序，不是最终视觉效果排名。如果真实折射是硬性验收条件，C 就不能作为最终完整方案；如果 A 能满足模糊与边缘约束，也没有必要为简单模糊直接上 B。

三、Q2：折射是否必须写 Shader？

这里要区分两件事：

位移计算：可以用 Direct2D 内置效果完成。

位移所使用的背景纹理：必须来自某个真实背景来源，否则只是扭曲自己画的材质。

Direct2D 的 CLSID_D2D1DisplacementMap 已经能够按照第二张位移图，对第一张输入图像进行空间重采样；它支持通过颜色通道控制 X、Y 方向的偏移。

所以，不应该一开始就写 HLSL，也不需要为了实现位移效果先增加 fxc 构建步骤。

最便宜的技术路线

背景纹理（GPU）

来自 A 的系统背板之外的独立捕获实验，或后续确定的背景来源

裁剪 + 轻度模糊

只处理胶囊需要的区域，并保留折射所需的边缘余量

Displacement Map

用预生成的位移图控制边缘的非均匀位移

高光 + 染色 + 原有内容

保留现有 Direct2D 文字、图标和动画

位移图可以先在 CPU 上生成一次，再上传 GPU；胶囊只是平滑变化形状时，不必每帧重建位移图。只有在确实需要动态改变透镜轮廓时，再更新参数或生成新图。

为什么暂时不写自定义 Shader？

在 720 × 60 DIP 的区域内，位移图本身并不大；真正未知的是捕获、同步、纹理共享和效果链的总成本。先用 D2D 内置位移效果，可以把“效果本身是否足够”与“背景从哪里来”拆开验证。

建议分两步：

B0：离线合成实验。 用静态背景图片作为输入，验证位移图是否真的能产生边缘透镜效果。

B1：实时背景实验。 只有 B0 的视觉效果通过，才接入实时捕获。

如果 B0 不够好，再评估自定义 HLSL。到那时我接受构建期增加 Shader 编译步骤，并把 .cso 作为程序资源，前提是运行时不需要额外 Shader 编译器或第三方运行库，并且把 Shader 的生成、版本、失败处理和发布检查纳入构建验收。

不过，自定义 Shader 不会自动解决背景捕获问题，也不一定比内置效果更快；不能仅凭“更底层”就认定它值得引入。

四、Q3：B 抓屏的实际成本、排除自身和反馈环
1. 先纠正一个关键预期：抓屏 API 不会只抓 720 × 60

DXGI Desktop Duplication 提供的是显示器输出的桌面图像纹理，并附带脏区域、移动区域等元数据。它支持在 GPU 侧处理图像，不需要把每帧回读到 CPU。
Microsoft Learn
+1

所以推荐的结构是：

从 DXGI 获取显示器纹理。

在 GPU 上将胶囊周围所需区域裁剪到局部纹理。

对局部纹理进行模糊、位移和合成。

将结果送入现有渲染链。

720 × 60 是我们希望处理的局部区域，不是 DXGI 保证只捕获的区域。Windows.Graphics.Capture 也应按实际捕获对象和运行模式验证，不能假设它天然提供局部桌面捕获。
Microsoft Learn
+1

2. 先算像素规模，不先猜性能

按 720 × 60 像素这个简化假设，60 FPS 时每秒处理约 259 万个像素样本；如果实际是 720 × 60 DIP，还要乘以 DPI 缩放系数的平方。

这只是输入规模，不是 GPU 耗时。实际成本取决于：

捕获纹理的尺寸与格式；

裁剪、模糊和位移各自的 GPU pass 数；

纹理是否需要跨设备或跨 API 复制；

显示器实际分辨率、DPI、刷新率；

背景变化是否频繁；

纹理同步和合成等待。

因此，不要把“区域小”直接等同于“成本低”。 先测一个只捕获并裁剪的版本，再加一遍模糊，再加位移；每次只增加一项。

可以作为探针，不能作为设计前提。

4. 逐帧改 region 会不会让捕获失效？

不能直接下这个结论。窗口 region、DWM 合成和捕获纹理是不同层次的问题；逐帧更新 region 本身并不等于捕获 API 必然失效。

但当前架构确实增加了几个需要测试的风险：

捕获帧与动画帧不同步；

旧位置残影；

胶囊被排除但卡片没有被排除；

高 DPI 或多显示器坐标换算错误；

捕获纹理更新频率低于渲染频率，导致玻璃背景看起来“粘住”。

因此 B 的第一版不应直接使用实时动画。先固定胶囊位置和大小，再打开动态宽度；最后才验证卡片滑出和多显示器切换。

五、Q4：旧规矩应该怎么改？

我建议改写规矩，而不是删除规矩。

旧规矩的问题是把“当前测试中背景模糊越界或无效”写成了永久禁止。这会阻止用户明确要求的视觉目标，但反过来，直接删除禁止条款也会让开发者在没有验收的情况下引入高成本方案。

建议在 ARCHITECTURE.md 中将规则调整为以下内容。

写作
液态玻璃与背景采样约束

IslandBar 默认使用原生 Win32 + DirectComposition + Direct2D/DirectWrite 自绘材质。液态玻璃效果应优先通过现有渲染路径实现，包括多层渐变、边缘高光、内外描边、环境染色和连续形变。

允许研究真实背景模糊或折射，但必须先通过独立探针验证，不得直接替换正式渲染路径。

任何真实背景效果必须满足：

背景模糊和折射不得泄漏到胶囊及目标形状之外。

不得产生自身捕获反馈、残影或持续累积的视觉错误。

不得引入未评审的运行时依赖、第三方框架或不必要的常驻进程。

必须实测 CPU、GPU、内存、帧时间、启动时间及动态窗口区域行为。

必须保留原有渲染路径作为可回退方案，并通过固定场景截图、像素区域分析和运行时回归检查。

任何新 Shader、捕获线程或效果链都必须纳入构建、资源生命周期、设备丢失和异常回退设计。

未经评审与用户确认，不得将实验路径合入正式渲染路径。

默认先实现不读取背景的液态材质；真实背景模糊优先验证系统背板路径；只有在真实折射确为目标且测量结果满足预算时，才允许引入 GPU 背景捕获和位移效果。

我暂时不建议把“每帧成本必须小于 X 毫秒”直接写死。因为不同 GPU、DPI 和刷新率下，绝对耗时并不具有同样意义。先建立当前版本基线，再根据实际机器和目标刷新率设定正式预算。

可以先采用以下实验门槛，不是永久架构指标：

空闲时不持续高频抓屏；

只有岛可见且确实需要背景效果时，才启用捕获；

对动态玻璃效果，先以 60 FPS 目标进行测量；

GPU 工作应有可测的预算，CPU 不得出现随捕获帧率持续上升的负担；

关闭效果后，捕获线程、纹理和相关资源必须能够及时释放。

六、Q5：验收标准怎么定？

你提出的“一张繁忙壁纸下的静息照片 + 一张卡片滑出照片 + CPU/GPU 前后数字 + 像素测量”是正确方向。我建议把它扩展为四组验收，避免只凭视觉判断。

第一组：视觉效果

V1：静息态

胶囊轮廓清晰，内部有真实的明暗层次。

背景内容能透过材质被感知，而不是被一层灰色完全盖住。

边缘具有厚度感和连续高光。

日期、时间、天气仍然清晰，不能因为染色而降低可读性。

V2：胶囊形变

从 220 到 720 DIP 时，边缘连续，不出现亮边断裂或瞬间变形。

高光随形状变化，不是简单把原有高光拉宽。

文字、图标和背景效果同步过渡，不产生明显错位。

V3：卡片从岛后滑出

胶囊和卡片的前后关系正确。

不出现胶囊边缘突然被卡片盖掉、玻璃材质跳变或残影。

卡片打开与关闭时，材质不会闪烁。

这些图只是视觉方向参考，不是 IslandBar 的实现结果。正式验收必须使用相同的真实壁纸、相同的窗口尺寸和相同的动画场景进行对比。

第二组：模糊泄漏与折射测量

沿用 HANDOFF 8.86 的边缘能量测量，但要补充基线：

关闭玻璃效果时拍摄基线。

打开效果后，在胶囊内部、边缘附近、胶囊外部三个区域分别测量。

记录每个区域的边缘能量变化，而不只是比较整张图的模糊程度。

对胶囊四角、顶部、底部和动画移动后的旧位置分别测量。

验收重点是：

胶囊内部应有可重复测量的背景处理效果。

胶囊外部不能出现可归因于本效果的额外模糊。

如果目标包含折射，还要通过高对比背景边缘的位置变化证明确实发生了空间位移。

最后一点很重要：仅有边缘高光、模糊和染色，并不能证明实现了折射。

七、Q6：真正影响“像不像苹果”的细节

我认为除了折射，还有四个容易被忽略的重点。

1. 玻璃不是越透明越好

如果整个胶囊都呈现相同透明度，它会更像普通半透明塑料。高级感主要来自不同区域具有不同的光学特征：

主体区域： 轻微染色，保留背景的辨识度。

上缘： 细而亮的镜面高光。

下缘： 较暗的厚度边缘，局部带有反射。

转角： 高光连续、曲率自然，不要像简单圆角矩形。

内部： 轻微明暗梯度，避免整个表面平坦。

不要先追求强烈彩虹边或夸张色散。色散过强容易显得像游戏 HUD，而不是系统级材质。

2. 高光应该跟随形状，而不是跟随矩形

你们已经有胶囊 220 → 720 DIP 的动态宽度，这是一个优势。

高光不应简单使用固定宽度的顶部白色渐变，再随着窗口整体拉伸。建议将材质参数和胶囊几何形状关联，让两端圆弧、长边和局部曲率有不同的反射强度。

第一版可以先用确定性的参数曲线和现有 Direct2D 几何完成，不必引入粒子系统。

3. 染色不应只取一次壁纸平均色

壁纸平均色可以作为低成本的环境色基准，但不能代表胶囊背后的实时内容。尤其是岛位于画面顶部时，背景可能刚好是浅色菜单、视频、亮色网页或深色桌面。

所以建议分两级：

C 路线： 使用主题色、壁纸平均色和明暗状态，成本低且稳定。

A/B 路线： 有真实背景信息时，再考虑根据采样区域的亮度与色调进行自适应染色。

自适应染色必须带平滑过渡，不能让鼠标移动或窗口刷新导致胶囊颜色快速跳动。

4. 动态形变比堆叠效果更重要

如果形状变化生硬，即使有真实折射也不会显得高级。现有岛的展开动画应该继续复用，不要为了玻璃效果重新发明整套窗口动画。

建议把形变拆成三个同步但独立的部分：

胶囊轮廓的宽度和曲率；

边缘高光的分布与强度；

内容布局、透明度和位置。

它们使用同一动画进度，但不必使用完全相同的插值曲线。这样可以让边缘先响应、内容稍后稳定，产生更自然的液态感。

八、最终决策与执行顺序
推荐方案：分阶段验证，不整体换渲染架构

第一阶段：C 路线，重做现有材质。

先优化主体染色、内外边缘、高光、厚度感与形变。保留现有渲染路径和主题机制。

第二阶段：A0，独立 Acrylic 胶囊探针。

验证圆角裁剪和模糊越界。若失败，记录结果并停止投入，不把它硬接入正式窗口。

第三阶段：B0，静态背景折射原型。

使用静态图片验证 D2D 内置位移图是否足够。此阶段不抓实时桌面，也不增加 Shader 编译步骤。

第四阶段：B1，实时捕获验证。

只有 B0 的折射效果通过后，才测试 DXGI 捕获、自身排除、纹理同步和 GPU 性能。

第五阶段：合入前评审。

对照视觉、像素泄漏、性能、回归四组结果，再决定最终采用 C、A 或 B 的组合。

我的最终立场是：

同意用户明确提出的液态玻璃目标，也同意重新评估原有的“不加背景模糊”限制。

反对直接把 Acrylic 塞进现有全宽窗口，或直接把实时抓屏和 Shader 效果链接入正式版本。

修正开发顺序为 C → A → B：先快速改善观感，再验证系统材质，最后才为真实折射承担复杂度。

保留原有渲染路径、构建约束、层方向检查和现有回归测试。

目前不需要改代码，也不需要立即接受任何新依赖。先完成 A0 和 C 路线的设计评审，拿到第一组照片与测量数据后，再决定是否进入实时折射阶段。
