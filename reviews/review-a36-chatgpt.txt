有两个关键技术问题，需要特别指出
第一，WH_CALLWNDPROC 的观察范围与生命周期必须经过验证。
它并不是通用的系统级托盘注册 API。钩子能观察到什么消息、覆盖哪些线程，以及模块在不同 Windows 版本下如何加载，都取决于实际的钩子安装方式和目标窗口消息路径。

• 验证真实 WM_COPYDATA 是否经过预期的 Explorer 窗口消息路径。

• 验证 Explorer 重启、模块禁用及重新启用后的行为。
• 验证 Windows 更新后观察失效时，产品能够降级而不是卡死。

建议将“只读”限定为：模块只观察注册信息、复制必要字段并发布快照，不修改目标应用的托盘注册状态，不篡改消息，不接管应用回调，不模拟应用执行逻辑。

Q3：单 EXE 安装器是否携带第二份 RCDATA DLL？
建议携带，但采用独立、可回退的模块部署
我的首选是：安装器仍然保持单 EXE，模块 DLL 作为独立资源嵌入安装器，在启用功能时释放到版本化目录；不要每次启动主程序时都重新释放 DLL。
需要区分两个概念：单 EXE 分发，不等于运行时只能存在一个文件。只要用户拿到的是一个安装器，安装后的主程序、模块和配置文件可以分开部署。
两种方案对比
￼
方案 A：安装器内嵌 DLL（推荐）
优点：
• 安装包自包含，离线安装时不依赖网络。
• 主程序与模块来自同一版本发布，便于验证版本一致性。
• 可以校验 DLL 哈希、签名及 ABI 版本。
• 升级流程由安装器统一管理。
失败模式：
• 释放路径不可写、磁盘空间不足或文件被占用。
• DLL 被安全软件隔离或加载失败。
• Explorer 仍映射旧 DLL，导致升级无法立即完成。
• 安装器损坏或资源版本不匹配。
￼
方案 B：主程序运行时释放到 %LOCALAPPDATA%
优点：
• 可按需释放，关闭功能时不必部署模块。
• 可以将模块版本独立管理，便于回退。
• 不需要把模块直接安装到应用程序目录。
失败模式：
• 目录权限、磁盘空间、杀毒软件或文件占用导致释放失败。
• 主程序每次启动都释放可能造成无意义的磁盘写入。
• 多实例同时释放、版本覆盖及校验竞态。
• 清理逻辑可能误删仍被 Explorer 使用的旧版本。
推荐的具体落地方式
1. 安装器将模块 DLL 作为第二份 RCDATA 载荷嵌入。
2. 首次启用 native 观察能力时，释放到类似以下路径：
%LOCALAPPDATA%\厂商名\产品名\modules\tray-observer\<版本>\tray_observer.dll
3. 释放前校验资源完整性；发布版本应验证签名或可信哈希，并在加载前确认 ABI 兼容。
4. 不直接覆盖正在使用的 DLL。每个模块版本使用独立目录，切换版本时更新主程序的版本指针或配置。
5. 如果模块释放、加载或 IPC 初始化失败，记录明确原因并自动降级，不阻止主程序启动。
6. 禁用模块后可以停止使用它，但不要在无法确认卸载状态时强行删除文件。
关于 PIN 住的问题： Explorer 映射 DLL 后，文件通常无法像普通未使用文件一样直接替换或删除。使用版本化路径比反复覆盖固定文件更可靠，也更容易回退。
还有一个必须先验证的部署前提：模块究竟由哪个进程、通过什么机制加载。若方案依赖 Explorer 内的钩子加载，DLL 的部署、位数、签名要求、钩子安装和卸载方式都必须与实际实现匹配。不能仅凭“DLL 已经释放”就认定观察模块已启用。

--dump 应如何处理？
我不建议把完整的实验版 --dump 原封不动地搬进产品，也不建议把它彻底删掉。
我的建议是将其拆分：
• 产品诊断接口：保留。 记录 uVersion、消息编码分支、目标窗口、调用结果、超时状态、观察到的窗口级证据及 ABI 版本。
• 底层协议诊断：保留为独立开发工具。 如果未来 Windows 更新导致托盘消息行为改变，应能够重新验证真实协议，而不是依赖过期的历史结论。
• 侵入式实验能力：默认不进入正式版本。 只读钩子、调试注入或其他具有宿主风险的实验机制，不应因保留 --dump 名称而自动成为产品功能。
需要注意：普通日志只能证明程序自己准备发送了什么，不能替代对实际协议的验证。如果未来还需要捕获 Explorer 实际发送的原始字节，应保留一个有明确安全边界、可独立构建的诊断工具及其复现说明。它可以放在开发工具目录，不必随安装包发布。
另外，历史文档应保留关键错误案例：错误的 v4 编码曾导致微信崩溃，正确编码则已在 Wallpaper Engine 上验证成功。这个对照比只保留成功日志更有价值。

托盘功能产品化与协议约束
1. 统一协议入口
• 所有托盘消息编码必须集中在 TrayInteraction 的唯一发送入口。
• 必须根据 uVersion 选择对应的消息编码规则。
• 禁止在 UI、业务逻辑、观察模块及其他文件中手写或复制托盘消息编码。
• 每种编码必须具有独立、可重复执行的回归测试。
• 任何协议修改必须附带实测依据、测试结果和回退方案。
2. 菜单检测与超时
• SendMessageTimeout 的超时只表示调用等待结束，不代表消息未投递、应用处理失败或菜单未出现。
• 250 ms 仅作为单次同步调用的等待上限，不得直接作为自绘菜单的触发条件。
• 必须使用窗口级证据判断原生菜单是否出现；优先检查新出现的 #32768 菜单窗口，并结合进程、创建时间、位置和可见状态进行关联。
• 禁止使用屏幕像素差作为菜单出现与否的主要判据。
• 兜底菜单必须考虑原生菜单延迟出现、重复右键和双菜单冲突。
• 所有等待和观察必须有明确截止时间，不得阻塞主 UI 线程。
3. 观察模块边界
• 不得向第三方应用注入代码，不得调用第三方应用的内部函数，不得篡改其托盘注册消息。
• Explorer 内模块仅执行必要的数据观察、字段校验和非阻塞发布。
• 不得创建工作线程、启动定时轮询或在消息回调中执行磁盘 I/O、图像加载、同步 IPC 等待及复杂操作。
• 模块必须定义 ABI 版本、结构体大小、消息类型和兼容性校验；不兼容时必须拒绝连接并安全降级。
• IPC 必须校验客户端身份、访问权限、消息长度及字段边界。
• 模块失效、主程序退出或 Explorer 重启不得导致主程序永久阻塞。
• 必须支持禁用、卸载、版本升级和回退；禁止直接覆盖仍被进程映射的 DLL。
• 模块启用、禁用和失联状态必须可诊断，且不得无限重试。
4. 产品运行模式
• off：关闭新增托盘观察与交互功能，保持已定义的现有行为。
• self：使用自绘托盘及统一交互入口。
• native：启用观察模块及相应兼容能力，并保留经过验证的原生托盘回退路径。
• 模式切换失败不得导致灵动岛主程序无法启动。
• 不得为了实现托盘功能引入不必要的常驻进程、线程或无界缓存。
5. 实验工具与产物
• 实验探针不得成为正式产品运行的必要依赖。
• 产品功能落地并通过验收后，必须删除已废弃的实验源码、脚本、截图中间产物及部署目录。
• 删除前必须检查构建配置、安装器资源、CI、文档和运行脚本，消除对废弃路径的依赖。
• HANDOFF、reviews、captures 中的有效证据和历史失败案例应保留。
• 必须保留可复现关键协议行为的诊断能力；侵入式实验工具应与正式产品隔离，不默认随安装包发布。
6. 交付验收
• 每次改动仍须遵循仓库既定的六步开发与验收流程，不得跳步。
• 验收必须覆盖 v0、v4、调用超时、延迟菜单、应用重启、模块禁用、Explorer 重启、安装升级和失败回退。
• 必须验证原生菜单与兜底菜单不会因延迟或重复操作产生不可控冲突。
• 所有未验证的兼容性结论必须明确标记，不得将推测当作实测结果。
• 只有在产品功能、回退路径、诊断能力和清理检查全部通过后，才允许删除实验探针及其产物。

Q4
同意验收后清理，但保留诊断能力。
删除实验探针与大体积产物，保留 HANDOFF、评审、截图及失败案例。--dump 应保留为经过整理的诊断能力，必要的低层协议验证工具独立维护。
