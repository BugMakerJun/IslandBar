一、 关于“注册 = WM_COPYDATA 发给 Shell_TrayWnd”的结论

表态：完全同意

判断正误：这个判断完全正确，逻辑闭环极强。

原理解析：在 Windows 架构中，所有应用调用 Shell_NotifyIcon 最终都要将扩展的 NOTIFYICONDATA 结构体序列化并投递给任务栏宿主（即 explorer.exe 的 Shell_TrayWnd 窗口）。通过在 explorer 进程内拦截到这临门一脚的 WM_COPYDATA，你直接绕过了所有应用端的沙箱隔离、代码完整性检查（Code Integrity）和权限壁垒。这是一个降维打击式的优雅方案。

二、 针对两类不理想情况的破局思路
1. 提权应用（如任务管理器，High 完整性）

为什么抓不到 / 点不动：虽然 High 进程向 Medium 进程（explorer）发消息理论上不违反 UIPI（向下发送允许），但任务管理器可能绕过了标准的 Shell_NotifyIcon 链路，或者其托盘由独立系统进程托管。

破解思路：

不要尝试去 Hook 任务管理器本身（会被 UIPI 和系统保护死死挡住）。

如果 explorer.exe 侧的 WM_COPYDATA 真的漏掉了任务管理器，可以尝试在 explorer 中通过托盘按钮枚举（向任务栏的 ToolbarWindow32 控件发送 TB_GETBUTTON 等消息）来直接抓取现有句柄和图标索引，或者监听 Shell 的 TaskbarCreated 广播消息强制触发一次全量刷新。

2. 没有发出过 ADD 的图标（如 NVIDIA 等常驻托盘服务）

原因：这些服务在你的钩子加载之前就已经完成了注册（ADD）。

破解思路：

增补“冷启动全量枚举”：模块在 explorer 里 PIN 住并初始化成功的第一时间，不要干等后续消息，而是主动去读一遍 explorer.exe 内部维护的托盘图标链表（通过经典的 Toolbar 控件逆向或 shell 内部 CTrayNotifyIcon 结构体）。只要拿到已有的 hWnd、uID 和 uCallbackMessage，缓存瞬间就能补齐，不需要等它们重新 ADD。

三、 关于“逐应用装模块”旧代码的处置

表态：同意保留开关，暂不永久删除

建议：代码不要物理删除，但将其设为宏控制或永久置假的配置项（例如 enable_legacy_per_app_hook = false）。

原因：虽然目前 shell 侧捕获 WM_COPYDATA 解决了绝大多数问题，但未来 Windows 大版本更新（或某些非标准托盘插件）可能会改变 shell 层的托盘消息分发机制。保留这段代码作为一个处于休眠状态的“备用回退通道”（Fallback），成本为零，但能提供极高的系统抗风险能力。

四、 模块常驻 explorer.exe 的四大风险提示

结构化异常处理（SEH）缺一不可

只要代码跑在 explorer.exe 内部，任何一次野指针、越界读取 WM_COPYDATA 载荷时的内存崩溃，都会直接带崩整个系统的任务栏和桌面。确保所有钩子回调函数内部必须包裹 __try / __except。

Windows 累积更新的破坏性

微软随时可能在月度更新中静默重构 explorer.exe 的内部托盘管理逻辑或 WM_COPYDATA 的分发路径。你的偏移量解析代码需要有健壮的边界检查（比如校验 cbData 长度是否符合预期），防止遇到未知结构时越界。

安全软件（EDR/杀软）的强力审视

尽管你的二进制有签名或行为纯净，但“将自定义 DLL 注入并长期 PIN 在 explorer.exe 中”属于高危行为。部分杀软的启发式扫描或企业级 EDR 可能会将其标记为进程注入行为。

内存泄漏（Leak）风险

如果在解析 WM_COPYDATA 时动态分配了内存但未正确释放，长年累月运行会导致 explorer.exe 内存缓慢增长。务必保持零动态分配或使用严格的栈内存。
