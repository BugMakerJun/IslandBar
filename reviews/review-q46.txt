第 51 轮评审请求（2026-10-16 深夜，IslandBar / Windows 11 26220）——**用户断言"就是灵动岛导致的"，要求解决**

用户原话：「我能确定是灵动岛导致的 你们给我解决了」。

这一轮的题目不是"再查一次"，而是：**在机制还没被证明的情况下，给出一个既能验证、又能解决问题的方案**。
请明确表态并排序。方案交用户拍板，确认前不动代码。

1. 事实（全部实测，一条一条都能复现）

  **四次弹出**：18:15、19:29、20:44、23:13（本地时间）。前三次间隔 74、75 分钟；第四次是在栏 22:32
  重启之后 **41 分钟**出现的——"75 分钟一次"这个规律**已经被打破**。

  **每一次的样子**：`SystemSettings.exe` 被创建，**父进程是 `svchost.exe`（DcomLaunch/BrokerInfrastructure
  那一组）**——即"代理激活"，调用者不写在事件日志里。窗口落在屏幕左上角 `(0,0) 362×329`（这是它自己的
  初始/加载窗；另有一个独立结论：Windows 给这个应用存的"正常矩形"就是 `(0,0) 362×329`，与栏无关）。

  **我们这边是干净的**：栏每次点磁贴 / 齿轮 / 声音页都会写一行
  `tile N 'X' -> ms-settings:... (result N)`；四次时间点前后**一条都没有**，栏日志里也没有任何点击记录。
  代码里 `ShellExecute("ms-settings:...")` 只有三处，全在点击路径上。

  **第四次抓到的现场**（升级后的守候脚本，出现前 60 秒内新建的进程）：
      23:12:46  backgroundTaskHost.exe  -ServerName:Global.Accounts.AppXqe94…mca
      23:12:46  backgroundTaskHost.exe  -ServerName:Global.DesktopSpotlight.AppXz2j…mca
      23:13:09  SystemSettings.exe      （23 秒后）
  `Global.Accounts` 这个名字指向"微软账户体验"那类后台任务。**这两个包在当前用户已安装清单和机器预置
  清单里都查不到**（发布者 id 是随机样子的、不带 Windows 签名）。

  **相关性与它的弱点**：栏开着时出现 4/4；栏停掉的 84 分钟（21:07–22:32）0/1。**但那 84 分钟用户多半
  人不在机器旁**，所以这不是干净的对照——"栏开着"和"人在用机器"这两个变量在现有数据里是绑在一起的。

  **我们做过什么"撒向全会话"的事（穷举，来自代码）**：
    ① 启动时（以及 explorer 换进程时）**向所有顶层窗口广播 `TaskbarCreated`**，让应用重新注册托盘图标
       （`shell/TrayLearn.cpp`，`SendMessageTimeoutW(HWND_BROADCAST, …)`）；
    ② 同一路径把 `island_tray_hook.dll` **注进 explorer** 并在 shell 的一个线程上装 `WH_CALLWNDPROC`
       观察钩子（模块自 PIN，只读注册消息）；
    ③ **隐藏 `Shell_TrayWnd` / `TrayNotifyWnd` / 所有 `Shell_SecondaryTrayWnd`**（默认模式）；
    ④ 每 5 秒读一次 `HKCU\Control Panel\NotifyIconSettings`（只读）；
    ⑤ 自己是一扇**置顶、全宽、360 高**的窗口，贴在屏幕顶部。
  **注意**：①②③ 都只发生在**启动那一刻**（③ 也只在启动那一刻），它们与 23:13 那次（启动后 41 分钟、
  期间 explorer 没换）**在时间上对不上**。所以如果真是我们，机制不在"我们周期性做了什么"，
  而在**"我们留下的那个状态"**（任务栏/通知区被隐藏、或 explorer 里多了一个模块）让 Windows 的某个
  提示流程改道去开设置页。

2. 候选机制（请判断哪个最可能，并指出我没列到的）

  M-A **通知区被我们隐藏 → Windows 的提示流程改道**：`TrayNotifyWnd`（通知角落）在我们手里是隐藏的；
    某个"要告诉用户一件事"的流程（账户/聚光灯/更新）原本靠通知区或 toast，取不到就**改开设置页**。
    反例：用户的两张截图里 "Restart to Update" 的 toast 是**看得见**的，说明 toast 未必失效。
  M-B **explorer 里多了一个模块 + 消息钩子**：模块在 explorer 里改了它的消息路径（哪怕只读），
    让 shell 的某个状态机走了另一条分支。
  M-C **`TaskbarCreated` 广播被收件人当成"shell 重启了"**：某些组件在 shell 重启后会重放自己的提示。
    但这次广播在启动那一刻，与 41 分钟后的弹出对不上（除非它影响的是"之后的第一次触发"）。
  M-D **置顶全宽窗口占了任务栏的位置**：shell/体验组件按"任务栏区域被占"做出某种降级。
  M-E **巧合**：真正的触发者是 `Global.Accounts`/`Global.DesktopSpotlight` 这类后台任务（它们由用户活动
    或系统定时器驱动），而"栏开着"只是恰好覆盖了"用户在用机器"的那些时段。

3. 我打算怎么做（请逐条表态，并给顺序）

  **第一步（诊断，不动产品行为）**：加一个环境开关（沿用现有 `ISLANDBAR_*` 家族，默认不生效），
  用来**分别关掉**：① 启动时的 `TaskbarCreated` 广播；② 把模块注进 explorer 的那一步。
  这样"我们做过的事"就能一项一项排除，而不是靠猜。

  **第二步（分段对照，每段约 40–60 分钟）**，每段都让用户**照常用机器**：
    A 段：`--keep-taskbar`（栏在跑，但**不隐藏任何东西**）→ 若不再出现，M-A/M-D 嫌疑最大；
    B 段：关掉模块/广播（栏在跑、任务栏照旧隐藏）→ 若不再出现，M-B/M-C 嫌疑最大；
    C 段：栏完全停掉、**用户活跃使用**（补上 21:07–22:32 那段的漏洞）→ 若照样出现，M-E 成立（不是我们）。

  **第三步（修）**，取决于第二步：
    * 若 M-A/M-D 成立：把"隐藏任务栏"换成"**保留但不显示**"——例如把 `Shell_TrayWnd` 移出可视区、
      或改成 2026-10-15 那版"**裁剪到只剩通知区**"的做法（当时的实测：裁剪好看、零成本），
      让 Windows 眼里**通知区始终存在**；
    * 若 M-B/M-C 成立：① 广播从"自动路径"里去掉，只留给显式的 `--tray-learn`；② 模块改为**只在需要
      按压托盘格时**才注入，或干脆默认不注入（代价：托盘页退回注册表列表，"哪些真的活着"这个判据变弱）。
